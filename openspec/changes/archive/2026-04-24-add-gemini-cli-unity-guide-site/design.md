## Context

目前專案尚未建立前端應用程式，只有 Spectra 設定與 proposal。這次變更要從零建立一個面向學生複習使用的教學網站，內容主題固定為 Windows 上安裝 Gemini CLI，並使用 Unity 2D 做出最小可玩版射擊遊戲 demo。

網站不是老師上課投影的主介面，而是學生在課後重新走流程、快速找到某一步、查看關鍵截圖、並複製指令與 prompt 的輔助工具。教材來源以既有 PPT/PDF 為主，步驟順序沿用原始章節，但會依操作目標合併成較少且較完整的教學 step。

主要限制如下：
- 第一版內容直接寫死在前端，不建立 CMS、Markdown 載入流程或後台。
- 每個 step 只顯示一張主圖，避免學生在同一步內還要切換多張圖片。
- 介面語言以中文說明為主，但工具名稱、指令、prompt、介面關鍵詞保留英文。
- 圖片資產可先使用現有教材截圖，後續再替換為重新整理的版本。

## Goals / Non-Goals

**Goals:**

- 建立一個可部署的單頁式教學網站，包含首頁與逐步教學閱讀體驗。
- 讓學生能用 Previous / Next 線性閱讀，也能透過章節或步驟索引快速跳回指定位置。
- 讓每個 step 以清楚的中文說明呈現一個明確操作目標，並可直接複製該步驟中的指令或 prompt。
- 保持教室教材感的視覺方向，避免過度產品化或遊戲化造成閱讀干擾。

**Non-Goals:**

- 不建立多教案入口、教師後台、內容編輯器或使用者帳號系統。
- 不在第一版支援多作業系統分支、深色模式、多語系或教材下載中心。
- 不在第一版追求高度動態互動，例如步驟內多圖輪播、註解標記編輯、或進度同步到雲端。

## Decisions

### Use Vite + React single-page guide shell

系統將使用 Vite + React 建立單頁式網站，並維持靜態部署友善的結構。專案目前沒有既有框架，因此選擇較輕量、啟動成本低、適合快速建立單一教學網站的組合。

選擇這個組合的原因：
- 網站內容固定，沒有伺服器渲染需求。
- 首頁與教學頁互動以前端狀態為主，React 足以支撐元件拆分與互動。
- Vite 的初始化與後續部署都簡單，適合從空專案快速落地。

不採用 Next.js 或 CMS 方案，因為目前沒有 SEO、後台編輯、或多內容來源整合需求，導入會增加不必要的複雜度。

### Store the lesson as typed chapter-and-step data

教學內容將集中在 src/data/guide.ts 之類的前端資料模組，以型別化的章節與步驟資料描述整個教材。每個 step 至少包含：章節資訊、步驟標題、操作目標、說明段落、單張圖片、以及零到多個可複製區塊。

這個決策能讓內容和畫面分離：
- 後續重新整理步驟切分時，只需調整資料，不必大量改動元件。
- 指令與 prompt 可統一用同一種 block schema 呈現與複製。
- 首頁章節摘要、步驟索引、主閱讀區都能共用同一份資料來源。

不直接把所有教學文字散落在各個元件中，因為那會讓後續維護和教材修訂成本變高。

### Provide overview navigation and linear navigation together

導覽會分成兩層：
- 首頁上的章節摘要與快速入口，用來讓學生理解整體流程並選擇起點。
- 教學頁內的線性 Previous / Next 與步驟索引，用來支援第一次跟做與課後回看。

教學頁必須同時顯示目前所在章節與步驟進度，並允許直接切換到任一步驟，而不是只依賴線性翻頁。這是因為網站定位偏向複習手冊，學生更常回來找特定段落，而不是完整重看。

不採用只有簡報式翻頁的模式，因為當步驟數量增加時，回到指定步驟的成本會過高。

### Render each step as one focused task with one hero image and copy blocks

每個 step 會對應一個明確的操作目標，而不是一張投影片。畫面包含：步驟標題、簡短說明、重點提示、單張主圖、以及可複製的指令或 prompt 區塊。若某一步沒有可複製內容，則不顯示複製卡片。

這個決策直接回應教學需求：
- 新手比較容易完成一個明確任務，而不是連續閱讀零碎提醒。
- 每步只放一張主圖，可降低視覺負擔，並強迫我們挑選最能代表該步的截圖。
- 複製區塊集中顯示，能讓學生快速執行而不必在段落中尋找命令列內容。

不採用步驟內圖片輪播或可複製整段說明文字，因為這些互動不是第一版的主要價值。

### Preserve PPT chapter order but merge slides into task-oriented steps

內容編排會保留原本教材的大章節順序，例如 Node.js、Gemini CLI、GEMINI.md / Context、Unity 實作、Spec，但網站中的 step 數量不直接等於投影片頁數，而是依學生操作節奏重新合併。

這樣做的原因：
- PPT 的頁數切分反映講解節奏，不一定適合學生實際執行。
- 將相鄰且屬於同一個操作目標的投影片合併，可讓網站步驟總數下降，降低導航成本。
- 章節順序不變，可讓老師在課堂上口頭對照既有 PPT，不會出現教材順序錯亂。

## Risks / Trade-offs

- [截圖清晰度不一致] → 第一版可先使用現有截圖，但需要在資料模型中保留 alt 文案與替換路徑，方便後續更換資產。
- [步驟合併過度] → 在整理 step 時必須以學生能否完成一個操作目標作為切分準則，避免單一步驟塞入過多動作。
- [單頁式網站深連結能力不足] → 導覽狀態需要反映在 URL 或可重建的前端狀態中，避免重新整理後失去目前步驟。
- [教室教材感與現代互動衝突] → 視覺要維持清楚親切，但仍要保留足夠的按鈕層級與狀態對比，避免看起來像靜態海報。

## Migration Plan

- 第一步建立前端專案骨架與資料模型。
- 第二步依教材整理章節與 task-oriented steps，先接入現有截圖與可複製內容。
- 第三步完成首頁、教學頁、導覽與複製互動。
- 第四步驗證學生能從首頁進入教學、跳轉指定步驟、以及成功複製指令。
- 這是新建功能，沒有既有線上版本需要資料遷移；若需回滾，只要停止部署新站點即可。

## Open Questions

- 最終的 step 合併數量需要在將 PDF/PPT 對應成資料模型時最後確認，但這不阻礙目前 proposal 與 spec 建立。
- 部分步驟是否需要補拍更清楚的 Unity 或 Gemini CLI 截圖，要在整理第一版內容時同步盤點。
